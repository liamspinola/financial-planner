👔 CTO — Decades of Experience

Verdict: TypeScript is the right call. One structural decision remains: shared types.

TypeScript strict mode eliminates an entire class of production bugs before they happen — especially important in a multi-user rewrite where user_id mismatches and wrong-shaped API responses are the most common failure modes. Good decision.

Monorepo shared types — decide now: You have a client (React) and a server (Express). Both will describe the same entities: Debt, IncomeSource, Expense, PlanResult. If you define them twice, they drift. Create a shared/types/ directory at the project root, export your domain types and Zod schemas from there, and import in both client and server. This is not a full monorepo — just a shared directory. No extra tooling needed.

financial-planner/
  shared/
    types/
      debt.ts       // Debt, Tranche, DebtWithTranches
      plan.ts       // PlanResult, StrategyComparison
      ai.ts         // AIMessage, AIProvider
      api.ts        // API request/response shapes
  client/src/       // imports from ../../shared/types
  server/           // imports from ../shared/types

Migration strategy: Don't migrate the existing JS to TypeScript line-by-line. You're already rewriting for multi-user — write the new code in TypeScript from scratch. The financial engine (pure calculation logic) is the one piece worth migrating carefully since it has no side effects and the types will catch real bugs.

⚙️ Senior Software Engineer — Decades of Experience

Verdict: Four TypeScript-specific decisions that need to be explicit in the plan.

1. tsconfig — strict mode, no compromise:

// tsconfig.json
{
  "compilerOptions": {
    "strict": true,           // enables all strict checks
    "noUncheckedIndexedAccess": true,  // arr[0] is T | undefined
    "exactOptionalPropertyTypes": true,
    "target": "ES2022",
    "module": "NodeNext",
    "moduleResolution": "NodeNext"
  }
}

2. Drizzle ORM is the right choice — here's why: Drizzle is TypeScript-first, generates types from your schema definition, produces type-safe queries, and generates SQL migration files you can inspect and run manually. Unlike Prisma, it doesn't require a separate binary and works natively in Vercel serverless. The schema definition doubles as your source of truth for both TypeScript types and SQL migrations.

3. Zod schemas → infer TypeScript types: Don't write types twice. Define Zod schemas for all API request/response bodies, then use z.infer<typeof schema> for the TypeScript type. One definition, both runtime validation and compile-time types.

const CreateDebtSchema = z.object({
  label: z.string().min(1).max(100),
  balance: z.number().positive(),
  interestRate: z.number().min(0).max(100),
});
type CreateDebtRequest = z.infer<typeof CreateDebtSchema>;

4. Financial arithmetic — use integer pence, not floats: The existing engine almost certainly uses floating point for monetary values. 0.1 + 0.2 !== 0.3 in JavaScript. For a financial app, store and calculate all monetary values as integer pence (multiply by 100 on input, divide by 100 on display). TypeScript won't catch this for you — it needs to be an explicit convention enforced by code review and documented in the shared types.

Verdict: TypeScript enables a cleaner AI provider interface. Define it explicitly.

The AI provider abstraction in TypeScript:

// shared/types/ai.ts
interface AIProvider {
  streamAnalysis(
    context: FinancialContext,  // typed, no raw strings
    userMessage: string,
    history: AIMessage[]
  ): AsyncIterable<string>;    // streams tokens
  readonly providerName: 'gemini' | 'anthropic';
}

// server/ai/providers/gemini.ts  — implements AIProvider
// server/ai/providers/anthropic.ts — implements AIProvider
// server/ai/providers/mock.ts  — implements AIProvider (tests)

TypeScript enforces that both real providers and the mock implement the same interface. If Gemini's SDK changes, the type error shows up at compile time, not in production.

FinancialContext type — the anonymisation contract in code: Define a FinancialContext type that explicitly excludes PII. The type itself documents what is and isn't sent to AI providers:

interface FinancialContext {
  // NOTE: No userId, email, or display name — by design
  debts: Array<{ label: string; balancePence: number; apr: number }>;
  monthlyIncomePence: number;
  monthlyExpensesPence: number;
  strategy: 'avalanche' | 'snowball';
  debtFreeDateEstimate: string;
}

If someone accidentally tries to add email to FinancialContext, the type definition makes it visible in code review. The anonymisation policy is enforced structurally, not just by convention.

Build pipeline: Client uses Vite (already configured, just add TypeScript). Server uses tsx for local dev (fast TS execution without compile step) and tsc --noEmit in CI to type-check. Vercel handles the server compilation for deployment automatically.

🤖 Senior AI Software Engineer — Decades of Experience

Verdict: Both SDKs are TypeScript-first. The migration from CLI subprocess is clean.

The Anthropic TypeScript SDK (@anthropic-ai/sdk) and Google's Generative AI SDK (@google/generative-ai) are both fully typed. Streaming is idiomatic — both support for await...of over typed chunk objects. No subprocess, no shell escaping, no JSON parsing of CLI output.

The existing Claude CLI integration is the most dangerous part of the current codebase from a security standpoint — it spawns a subprocess with user-influenced arguments. TypeScript + SDK replaces this entirely. The new code will be simpler, safer, and testable.

Prompt template typing: The prompts that currently exist as strings mixed with template literals should become typed functions:

function buildAnalysisPrompt(ctx: FinancialContext): string {
  // TypeScript ensures ctx has the right shape
  // FinancialContext excludes PII by type definition
  return `Analyse this debt payoff plan: ...`;
}

One remaining concern — prompt regression testing: When you migrate from Claude CLI to Gemini SDK, your prompts will produce different output. This isn't a bug — it's expected — but you should review the AI responses manually with realistic test data before releasing to your brother. Keep a set of "golden" financial scenarios and compare output between old and new providers. This is a one-time QA step, not ongoing infrastructure.

🧪 Senior QA Automation Engineer — Decades of Experience

Verdict: TypeScript + Zod closes the testing gap on input validation. Three test types to add.

TypeScript in tests: All test files (Jest unit tests + Playwright E2E) should be TypeScript. Typed mocks, typed fixtures, typed assertions. The MockAIProvider implementing the AIProvider interface means TypeScript will tell you when the mock drifts from the real interface.

Three test categories to add that don't exist yet:

  1. Type-level tests (tsd or vitest type tests): Assert that FinancialContext does not have a userId field. Assert that AIProvider.streamAnalysis returns AsyncIterable<string>. These are compile-time assertions that catch interface regressions.
  2. Drizzle migration tests: Run each migration on a clean Neon branch, verify schema matches expectations, run down migration, verify rollback. Part of CI on every PR that touches drizzle/.
  3. Financial calculation precision tests: The pence convention must be tested explicitly. Add unit tests that verify 0.1 + 0.2 edge cases don't corrupt amortisation totals over a 5-year simulation.
