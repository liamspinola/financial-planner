👔 CTO — Decades of Experience

Verdict: Promote mobile layout to v1 blocker. Everything else is irrelevant if the app doesn't work on the only device your user has.

The expert panel has spent four rounds discussing auth, AI providers, GDPR, TypeScript, and deployment — all of which are important — but none of it matters if the app renders unusably on a 390px screen. This is the most critical gap found across all reviews.

Strategic choice — don't just patch, go mobile-first: The temptation is to add responsive breakpoints as a quick fix. Don't. The current component tree was designed desktop-first. Patching it with `md:hidden` and `hidden md:flex` will produce a fragile, inconsistent experience. The right move is to redesign the layout as mobile-first (base styles = phone, `md:` = desktop enhancement) as part of the TypeScript migration. You're already rewriting the components for TypeScript — do the mobile layout at the same time. Not separately, not later.

Bottom navigation vs hamburger menu: Most mobile finance apps (Monzo, Emma, Plum) use a bottom tab bar, not a hamburger. For your brother, bottom navigation is more discoverable and easier to reach with one thumb. This is a product decision, not just a technical one — make it deliberately.

⚙️ Senior Software Engineer — Decades of Experience

Verdict: Systematic fix list — not a one-liner patch.

The Tailwind mobile-first rule: In Tailwind, unprefixed classes apply to all sizes. Responsive prefixes (md:, lg:) apply at that breakpoint and above. The correct pattern is: write mobile styles first (no prefix), then layer desktop styles (md:). The current codebase does the opposite — desktop styles are the default, mobile is not considered.

// Current (desktop-first, broken on mobile):
<div className="flex min-h-screen">
  <Sidebar className="w-56" />

// Fixed (mobile-first):
<div className="flex flex-col md:flex-row min-h-screen">
  <Sidebar className="hidden md:flex md:w-56" />
  <BottomNav className="fixed bottom-0 md:hidden" />

Specific fixes needed across the codebase:

  • App layout: flex-col md:flex-row, sidebar hidden md:flex, bottom nav on mobile
  • All fixed-width inputs: replace w-36/w-28 with w-full or flex-1 min-w-0
  • Form rows: flex-col sm:flex-row so controls stack on narrow screens
  • Budget table: wrap in overflow-x-auto container
  • Plan chart: remove hardcoded 680px width, use ResponsiveContainer width="100%"
  • AI advisor panel: stack vertically on mobile (flex-col md:flex-row)
  • All touch targets: minimum min-h-[44px] on interactive elements
  • Typography: verify readability at mobile scale — some labels may be too small

TypeScript migration timing is an advantage here: Since you're already rewriting components to TypeScript, mobile-first refactoring happens in the same pass. The total work is less than doing them separately.

🏗️ Senior Solutions Architect — Decades of Experience

Verdict: Navigation architecture decision drives everything else — make it now.

The sidebar is the root of the component tree. Every view is a child of the layout that includes the sidebar. Changing the navigation pattern is a structural change that affects every screen. This is not a CSS tweak — it's an architectural change that needs to be decided before components are written in TypeScript.

Two viable navigation architectures:

Option A: Bottom tab bar (mobile) + sidebar (desktop)
Bottom nav shows 4–5 key sections. Sidebar shows on md+ breakpoint. Same routes, different chrome. Standard pattern for finance apps. More discoverable for non-technical users.
Option B: Hamburger drawer (mobile) + sidebar (desktop)
Hidden off-screen drawer slides in on hamburger tap. Simpler to implement, familiar pattern. Less discoverable — non-technical users may not find the hamburger.

Recommendation: Option A. Bottom tab bar is the right choice for a non-technical phone user. It's always visible, always reachable with one thumb, and matches every finance app they've seen. Add it to the implementation plan now.

🤖 Senior AI Software Engineer — Decades of Experience

Verdict: AI chat interface has specific mobile problems that need direct attention.

Virtual keyboard problem: On mobile, when the user taps the AI chat input, the virtual keyboard appears and can reduce the visible viewport height by 40–60%. If the chat interface uses fixed heights or h-screen, the input box will be hidden behind the keyboard. Use dvh (dynamic viewport height) units instead of vh, and ensure the chat scroll container adjusts when the keyboard appears.

/* Use dynamic viewport height for chat container */
.chat-container {
  height: 100dvh; /* adjusts when keyboard appears */
  /* not: height: 100vh */
}

Streaming on mobile networks: SSE streaming works on mobile networks but can stall on poor connections. Add a connection timeout — if no token received within 10 seconds, show a "Connection slow — tap to retry" message rather than an infinite loading state.

Touch-friendly AI input: The chat text input needs min-h-[44px], adequate font size (minimum 16px to prevent iOS auto-zoom on focus), and a clearly tappable send button. These are easy to miss when designing on desktop.

🧪 Senior QA Automation Engineer — Decades of Experience

Verdict: Add mobile viewport to every Playwright test — not just a dedicated mobile test suite.

The instinct is to create a separate "mobile test suite." Don't. Every feature test should run at both desktop and mobile viewport. If a feature works on desktop but breaks on mobile, you want to know immediately — not when it's caught in a dedicated mobile sweep.

// playwright.config.ts
projects: [
  { name: 'desktop', use: { viewport: { width: 1280, height: 720 } } },
  { name: 'mobile', use: devices['iPhone 14'] },  // 390×844
  { name: 'android', use: devices['Pixel 7'] },   // 412×915
]

Specific tests to add for mobile:

  • Bottom nav: all tabs are tappable and navigate correctly at 390px
  • Debt form: all inputs are accessible and submittable with virtual keyboard open
  • Budget table: scrolls horizontally without breaking layout
  • AI chat: input is visible when keyboard is open, streaming renders correctly
  • Plan chart: renders at full width with no horizontal overflow

Visual regression testing: For the mobile layout refactor, consider adding Playwright screenshot comparison tests for the key views at 390px. This catches CSS regressions that functional tests miss.
