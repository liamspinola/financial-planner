Three Approaches to Multi-User Distribution

Which direction fits your goals? Select the one you prefer.

A

Hosted Web App + PWA Recommended

Deploy the existing app to the cloud with user accounts. Your brother opens a URL, logs in, and adds it to his phone's home screen — it feels like an app. One codebase. One deployment. Scales to many users.

Pros

  • Reuses ~90% of existing code
  • Works on every phone (iOS + Android)
  • No app store — instant updates
  • Scales from 2 users to 2,000
  • One codebase to maintain
  • Hosting costs ~$5–15/mo (Railway, Render, Fly.io)

Cons

  • Requires auth + cloud DB migration (SQLite → Postgres)
  • Ongoing hosting cost
  • Less "native" feel than a real app
Stack changes needed: Add auth (Clerk or Auth0), migrate to PostgreSQL, deploy to Railway/Render, add PWA manifest. Claude AI switches from CLI subprocess → Anthropic API.
B

Native Android App (React Native)

Rewrite the UI in React Native, sharing some business logic. Published to the Google Play Store. Your brother installs it like any app. Data stored locally on-device (no cloud sync).

Pros

  • Best native phone experience
  • Offline-first — no internet needed
  • No hosting costs (data lives on device)
  • Familiar "install from Play Store" flow

Cons

  • Significant rewrite — React Native ≠ React web
  • Google Play Store setup + review process
  • Two separate codebases to maintain
  • iOS excluded (would need separate Apple Dev account)
  • Updates require store review cycle
  • No path to web product without more work
Stack changes needed: React Native rewrite, Expo or bare workflow, SQLite on-device, Google Play Developer account ($25 one-time). Claude AI would need Anthropic API key per user.
C

Self-Hosted Docker Image

Package the app as a Docker image. Anyone technical enough can spin up their own private instance. Your brother would need someone to set it up for him (e.g., you deploy a copy on a cheap VPS just for him).

Pros

  • Minimal code changes to existing app
  • Each user gets fully isolated instance
  • Open source friendly
  • No shared infrastructure to maintain

Cons

  • You'd need to manage separate VPS per person
  • Doesn't scale — operational nightmare beyond a few people
  • Still needs a domain/URL for phone access
  • Dead end for a real product
  • No path to option C (product) from here
Stack changes needed: Dockerfile, nginx config, VPS setup per user. Manageable for 2–3 people, breaks down fast beyond that.
Expert panel verdict: All six perspectives align on Option A. It reuses what you've built, scales to a real product, works on every phone without an app store, and the code changes are well-defined. The Android route (B) only wins if offline-first is a hard requirement — and even then, a PWA with service workers gets you most of the way there.
