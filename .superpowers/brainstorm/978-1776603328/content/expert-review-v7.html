👔 CTO — Decades of Experience

Verdict: Spec is solid and complete. Two gaps to close before implementation starts.

Gap 1 — No rollback strategy for database migrations. The spec says "Drizzle generates up + down migration files" in the architecture section but never mentions how a failed migration is recovered from. Production migrations are the single highest-risk operation in this entire plan. The spec should state explicitly: (a) take a Neon point-in-time snapshot before running any production migration, (b) test the down migration on a Neon branch before touching production, (c) never run a destructive migration (DROP COLUMN/TABLE) without a named restore point. One paragraph. Without it, an implementer could run migrations without these safeguards and have no recovery path.

Gap 2 — No app name. The PWA section specifies icons, manifest fields, and display modes — but the app has no name in the spec. The manifest.json needs a name. The browser tab needs a title. The home screen icon needs a label. This is a product decision that should be made before implementation, not discovered when someone goes to write the manifest. What is this app called?

What's good: The decisions table is crisp and complete. The release checklist is the right gate. The phase breakdown is well-sequenced — each phase has clear dependencies on the previous. The cost table is accurate. This is the most thorough spec I've seen for a side project of this scope.

⚙️ Senior Software Engineer — Decades of Experience

Verdict: Three implementation details missing that will cause ambiguity during coding.

Detail 1 — How does Vercel serve the Express API? The spec says "Vercel (frontend + serverless API)" and mentions vercel.json in the files list — but never explains the adapter pattern. Express doesn't run natively as Vercel serverless functions. The implementer needs to know the approach: use @vercel/node with a single api/index.ts catch-all that imports the Express app. Without this, Phase 7 will stall. Add one line: "The Express app is exported as a single Vercel serverless function via api/index.ts using @vercel/node. All routes under /api/v1/ are handled by this function."

Detail 2 — Where does the Drizzle schema reference Supabase Auth users? The spec says every table gets user_id UUID NOT NULL REFERENCES auth.users(id) ON DELETE CASCADE. But Supabase Auth's auth.users table is in a separate schema managed by Supabase — you cannot directly foreign-key to it from application tables in the public schema on Neon (a separate database). The correct approach: Supabase issues a JWT containing the user's UUID; the app trusts and stores that UUID as user_id without a DB-level foreign key constraint. The isolation is enforced at the application layer (middleware + WHERE clauses), not by DB referential integrity. The spec's FK syntax is wrong and will confuse the implementer. Fix the data model section.

Detail 3 — tsconfig.json module resolution for shared types. The spec mentions shared/types/ but doesn't explain how both client/ and server/ import from it. With "moduleResolution": "NodeNext" this requires path aliases in each tsconfig. Add a note: "Both client/tsconfig.json and server/tsconfig.json define a path alias @shared/* pointing to ../../shared/*. Vite's resolve.alias also needs the same mapping for client builds."

🏗️ Senior Solutions Architect — Decades of Experience

Verdict: The Neon + Supabase split needs one more sentence of justification, and the connection pooler detail is buried.

Neon vs Supabase PostgreSQL — clarify why split: A reader coming fresh to this spec will ask: "Why are we using Neon for the database AND Supabase for auth? Why not use Supabase for both?" The spec doesn't answer this. The reason (Supabase free PostgreSQL pauses after 7 days of inactivity; Neon does not) should appear as a one-liner in the Decisions table or the Data Model section. Without it, the split looks accidental rather than deliberate, and a future implementer might "simplify" it by moving everything to Supabase PostgreSQL and reintroduce the pausing problem.

Neon pooler connection string — not mentioned in Phase 1. The spec correctly calls out DATABASE_URL as the "Neon pooler connection string" in the env vars table, but Phase 1 (Database setup) never mentions it. An implementer setting up Neon will be given two connection strings — direct and pooler — and may use the direct one. Add to Phase 1 step 1: "Use the pooler connection string (PgBouncer endpoint), not the direct connection. Vercel serverless functions open a new DB connection per invocation; the direct connection exhausts Postgres connection limits under concurrent load."

What's well-architected: The FinancialContext type as a compile-time anonymisation contract is genuinely elegant — it's the right use of TypeScript's type system for a non-functional requirement. The SSE pattern is correctly specified. The AI router abstraction is clean and testable. The env var scope column (server only / client / both) is exactly the right level of detail — I've seen production incidents caused by missing that column.

🤖 Senior AI Software Engineer — Decades of Experience

Verdict: AI section is well-specified. One gap: the FinancialContext shape is incomplete for the actual prompts.

FinancialContext is illustrative, not complete. The spec shows a simplified shape with 5 fields. The actual financial planner has tranches (promotional rates + standard rates), windfall events, expense events, spending actuals, progress snapshots, and strategy comparison results. The prompts that produce good AI narratives need this richer context. The spec should note: "The FinancialContext interface shown is the PII-exclusion contract. The full implementation will include additional fields (tranches, windfalls, expense events, strategy comparison) — all financial figures, none personally identifying." Without this note, an implementer might treat the spec's simplified version as the complete definition and build prompts around it, then discover the output quality suffers because key context is missing.

Gemini EU endpoint: The spec says "EU API endpoint" for GeminiProvider but doesn't name it. Google's Gemini API does have regional endpoints (europe-west1-aiplatform.googleapis.com). However, using the regional Vertex AI endpoint requires a Google Cloud project and service account — it's meaningfully more complex than the standard AI Studio API key approach. The simpler alternative: use the standard Gemini API (which routes globally but Google's data processing terms cover GDPR compliance) and note this explicitly so the implementer doesn't spend time on Vertex AI setup unnecessarily. Recommend: use standard AI Studio endpoint, document that Google's API terms provide GDPR-adequate data processing commitments. Add this clarification to the spec.

Golden outputs directory: The spec mentions server/ai/prompts/golden-outputs/ — good. Add one line: these files should be committed to the repo and not gitignored. They are the regression baseline and need to survive machine changes.

🧪 Senior QA Automation Engineer — Decades of Experience

Verdict: Testing strategy is thorough. Two gaps.

Gap 1 — No test for the migration harness itself. The spec says "migration testing harness: seed SQLite → run migration → verify row counts match → verify amortisation totals identical." But who runs this? When? It should be a named npm script (npm run test:migration) that runs as part of the Phase 1 acceptance criteria — not just a manual check. Add to the spec: "Migration harness runs as npm run test:migration. Must pass before Phase 1 is marked complete. Not part of regular CI (runs once, on a real Neon branch)."

Gap 2 — No mention of test data seeding strategy for E2E tests. Playwright tests that exercise "add debt, run plan, use AI" need a consistent starting state. How is this achieved? Options: (a) each test creates its own data via API calls in beforeEach, (b) a shared seed script populates the test database before the suite runs. The spec should specify which approach. Recommendation: option (a) — test creates its own user + data, no shared state between tests. This makes tests order-independent and parallelisable. Add one sentence to the testing strategy.

What's correct: Running Playwright at three viewports simultaneously is the right call. The cross-user isolation test pattern is exactly right (returns 403, not 404 or 200). The rate limit test verifying 429 not 500 is a subtle but important distinction. The migration testing harness concept is the correct approach for a SQLite → Postgres migration.

📋 Senior Product Manager — Decades of Experience

The app has no name. Agreeing with the CTO. Before the manifest is written, someone needs to decide: what is this called? "Debt Planner," "ClearDebt," "PayOffPlan," something else? This affects: the PWA manifest name (shown on home screen), the browser tab title, the login page heading, the privacy policy, the app store listing (if it ever goes there). It's a 30-second decision that blocks multiple implementation tasks. Make it now, put it in the spec.

Privacy policy timing: The spec says "privacy policy required before any external user" and lists it in the release checklist. Good. But Phase 6 (GDPR) says "write privacy policy (use Termly)." The release checklist gates on "privacy policy live and linked in app footer." What's the URL? Where does it live? Options: a static page at /privacy within the app, or an external URL (Termly hosts it). Specify which — the implementer needs to know where to link from the footer.

What's well-considered: The v1 / v2 / v3 scope split is realistic and well-judged. Deferring the onboarding wizard to v2 is correct — empty states in v1 provide enough guidance for a first user. The hero metric (debt-free date above fold) is the right product decision. The AI opt-in consent flow protects both the user and the developer. This spec reflects genuine product thinking, not just engineering decisions.
