Data Anonymisation & Protection

Financial data is sensitive PII. Here is every layer that needs to be addressed.

Important distinction: True anonymisation makes data impossible to re-identify — it falls outside GDPR entirely. Pseudonymisation replaces identifiers with tokens but the data is still personal. Encryption protects data from third parties but the app itself can still read it. A financial planning app cannot fully anonymise its data and remain useful. What you can do is minimise, pseudonymise, protect, and isolate at every layer.

Layer 1 — What Data You Actually Collect (Minimise First)

Necessary — collect this
  • Debt amounts, interest rates, minimum payments
  • Income figures (to calculate budget)
  • Monthly expense categories and amounts
  • Windfall / lump sum events
  • Chosen payoff strategy
  • Auth identity (email via Supabase — required)
Do NOT collect — remove from scope
  • Bank names or account numbers
  • Credit card numbers or sort codes
  • Real name (auth gives you email — enough)
  • Date of birth
  • Precise location
  • Device fingerprint or IP address (beyond rate limiting)
  • Anything not directly needed for the calculation

Layer 2 — Database (Neon)

Neon encrypts at rest by default (AES-256) — this protects against someone stealing the physical disk. It does not protect against a compromised database connection or a misconfigured query that leaks another user's data. The real protection here comes from your application layer.

What to add on top:

  • Never store real names. The auth user_id (a UUID) is your identifier. Display names can be set by the user but store them separately and never join them into financial queries.
  • Separate PII from financial data. Keep a user_profiles table (display name, preferences) entirely separate from debts, income_sources, expenses. If the financial tables are ever exposed, they contain amounts and categories — not names tied to those amounts.
  • Debt labels are user-controlled — don't over-read them. A user might name a debt "Barclays credit card." That's their choice. You don't need to validate or store institution names separately — whatever they type is what gets stored.

Layer 3 — AI Providers (Biggest Risk)

This is the hardest part. When you send your brother's debt figures to Gemini or Anthropic, that data leaves your infrastructure and enters Google's / Anthropic's. You cannot control what happens to it there — only what you agree to contractually.

What to do:

  • Use the API, not the consumer product. Google's AI Studio API (what Gemini Flash uses) processes data under their API terms, which include data protection commitments and explicit statements that API data is not used to train models. This is different from using Gemini.google.com directly.
  • Strip identity before sending. The AI prompt should never contain the user's email address or display name. Send financial figures and categories only. Instead of "John Smith earns £3,200/month," send "The user earns £3,200/month."
  • Minimum necessary data in prompts. Don't send the full financial picture for every question. If the user asks about one debt, send only that debt's details — not all debts, not income, not the full history.
  • Disclose this to users explicitly. Your privacy policy must state: "When you use AI features, your financial data (excluding your name and email) is sent to [Google / Anthropic] for processing. This data is not used to train their models." Users must consent to this before they can use AI features.
  • Make AI features opt-in. The app should function fully without AI. Users who don't want their data leaving your infrastructure can still use the debt calculator, amortisation, and strategy tools. AI is an enhancement, not a requirement.

Layer 4 — Logging & Error Monitoring

Sentry and server logs must never contain financial data. Configure explicit scrubbing rules:

  • Sentry: use beforeSend hook to strip any event containing financial field names (amount, balance, income, debt)
  • Server logs: log route names and status codes — never request bodies
  • Vercel function logs: set log level to WARN+ in production — info-level logs often contain too much
// Sentry configuration
Sentry.init({
  beforeSend(event) {
    // Strip any extra context that might contain financial data
    delete event.extra;
    delete event.request?.data;
    return event;
  }
});

Layer 5 — User Controls (GDPR Rights)

Right to access
User can export all their data as JSON. One button in Settings.
Right to erasure
Delete account cascades all tables. Immediate. No "we'll process in 30 days."
Right to rectification
Users can edit all their data (already works by design).
AI conversation deletion
Users can clear their AI chat history independently of their account. Separate control.
