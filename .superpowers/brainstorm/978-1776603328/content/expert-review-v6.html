🎨 Senior UI/UX Engineer — Decades of Experience

Verdict: Three issues that will make the app feel broken on real iPhones, plus four UX gaps.

Issue 1 — Safe area insets (will clip bottom nav on every modern iPhone): iPhones with Face ID have a home indicator bar at the bottom of the screen. Without CSS safe area insets, your bottom nav will sit underneath it — partially obscured and with the last 34px of tap target cut off. This affects every iPhone since the X (2017). Fix:

/* In manifest.json */
"display": "standalone"  // required to enable safe area APIs

/* In global CSS */
:root {
  --sat: env(safe-area-inset-top);
  --sab: env(safe-area-inset-bottom);
}
.bottom-nav {
  padding-bottom: calc(0.5rem + env(safe-area-inset-bottom));
}
.page-content {
  padding-bottom: calc(4rem + env(safe-area-inset-bottom)); /* above bottom nav */
}

Also add <meta name="viewport" content="width=device-width, initial-scale=1, viewport-fit=cover"> — without viewport-fit=cover the safe area APIs don't activate.

Issue 2 — Numeric keyboard for monetary inputs: When your brother taps a debt amount field on his phone, he'll get a full QWERTY keyboard by default. Fix: use type="text" inputmode="decimal" on all monetary and percentage inputs. Do NOT use type="number" — it shows increment arrows on desktop, has inconsistent decimal separator handling across locales, and causes iOS to show a different keyboard than expected.

<input type="text" inputmode="decimal" placeholder="0.00" />  ✅
<input type="number" />  ❌ (wrong keyboard, locale issues)

Issue 3 — Dynamic Island / notch top padding: The top of the app also needs safe area treatment. If you have a fixed header or nav bar, it will sit behind the Dynamic Island on iPhone 14 Pro+. Add padding-top: env(safe-area-inset-top) to the top nav/header.

UX Gap 1 — Empty states: Your brother's first screen after login will be an empty dashboard. What does he see? Right now: probably empty charts, zero values, and no guidance. Design explicit empty states for each tab with a clear call to action. For the Debts tab: "No debts yet — tap + to add your first debt." For Plan: "Add your income and at least one debt to see your payoff plan." These take an hour to build and completely change the first impression.

UX Gap 2 — The hero metric: The most motivating number in a debt planner is the debt-free date. It should be the first thing your brother sees when he opens the app — large, prominent, above the fold. "You'll be debt-free by March 2028" is more powerful than any chart. Make this the focal point of the Plan tab on mobile, not a small stat buried in a row.

UX Gap 3 — Loading states: Financial calculations and AI responses take time. A blank area that suddenly fills is jarring. Add skeleton loading states (animated grey rectangles in the shape of the content) for the plan summary and AI responses. Tailwind's animate-pulse with placeholder shapes is sufficient — no library needed.

UX Gap 4 — Currency formatting: Use Intl.NumberFormat('en-GB', { style: 'currency', currency: 'GBP' }) everywhere money is displayed. Never format currency manually with string concatenation. This handles edge cases (£1,234.56 vs £0.50) and is locale-correct.

👔 CTO — Decades of Experience

Verdict: Phase 8 is in the wrong place. And the plan needs a definition of done.

Move prompt regression to Phase 4: Prompt regression review is currently Phase 8 — after deployment. That's backwards. If Gemini produces low-quality financial narratives compared to Claude, you need to know during Phase 4 (AI Layer), not after you've deployed to production and your brother is using it. Move it: Phase 4 step 10 should be "verify prompt quality with golden scenarios before proceeding — this is a gate, not a post-check."

Definition of done for v1: The plan lists phases but doesn't define when v1 is "ready to send to your brother." Add a release checklist:

  • All Playwright tests pass (desktop + mobile viewports)
  • tsc --noEmit passes with zero errors
  • npm audit — zero high/critical vulnerabilities
  • Lighthouse: 90+ Performance (mobile), 100 PWA
  • Manual smoke test on real Android phone (not emulator)
  • Privacy policy live and linked in app footer
  • Account deletion tested end-to-end
  • UptimeRobot monitoring active

Top 3 implementation risks:

  1. Gemini prompt quality — Claude CLI → Gemini may produce noticeably worse financial narratives. Mitigation: gate on Phase 4, adjust prompts before proceeding.
  2. Vercel 10s timeout under load — AI streaming via SSE should be fine, but if a response takes longer than 10s to start streaming the first token, Vercel will 504. Test with realistic prompts.
  3. SQLite → Postgres float precision migration — existing financial data may have float precision issues that go unnoticed until you compare outputs. The migration harness must catch this.

🤖 Senior AI Software Engineer — Decades of Experience

Verdict: Prompt regression must gate Phase 4 completion, not Phase 8.

Agreeing with the CTO: the prompt regression review cannot be the last phase. Here's why — if Gemini produces low-quality output, you'll need to iterate on prompts. That iteration loop belongs in Phase 4 where the AI layer is being built, not after you've done PWA work, security work, GDPR work, and deployed. The cost of discovering bad prompts late is days of rework in a phase you thought was complete.

Recommended: Capture Claude CLI output NOW before Phase 4 begins. Run 3–5 realistic scenarios through the existing Claude CLI today, save the outputs to server/ai/prompts/golden-outputs/. These become your quality baseline. Then during Phase 4, compare Gemini output to these saved examples before marking Phase 4 as done.

SSE first-token latency check: Add to Phase 4 verification — measure time to first token from Gemini. If it exceeds 5 seconds on a realistic prompt, investigate. Vercel's 10s timeout means you need some headroom. The Gemini SDK's streaming API starts yielding tokens faster than waiting for the full response, so this should be fine — but verify it explicitly.

🧪 Senior QA Automation Engineer — Decades of Experience

Verdict: Add empty state tests and skeleton loading tests. These are commonly skipped and commonly broken.

Empty state tests: After the empty state designs are built (per UI/UX recommendation), write Playwright tests that assert: a new user (freshly registered, no data) sees the empty state CTA on each tab, not a blank screen or error.

Skeleton loading tests: Test that the skeleton appears immediately on page load before data arrives (mock a slow API response with page.route() in Playwright to introduce a 500ms delay) and disappears once data loads.

Currency formatting tests: Unit test the Intl.NumberFormat currency formatter with edge cases: £0, £0.01, £1,000, £1,000,000, negative values (for display). Format bugs in financial apps erode user trust fast.

Safe area inset visual check: Can't be automated easily — add it to the manual release checklist: "Open app on physical iPhone, verify bottom nav is not clipped by home indicator, verify top header is not clipped by Dynamic Island."

📋 Senior Product Manager — Decades of Experience

Verdict: Empty states and hero metric are the highest-impact UX items in v1.

The UI/UX engineer is right about both. The hero metric (debt-free date, prominent and above the fold) and empty states (clear CTAs for a blank account) are the difference between your brother opening the app and immediately understanding its value, versus opening it and staring at zeroes wondering what to do.

This replaces the need for an onboarding wizard in v1. If the empty states are well-designed — "Add your first debt to get started" with a prominent button — your brother will know what to do without a wizard. The wizard (originally flagged as v2) can stay in v2. The empty states are simpler to build and achieve 80% of the same effect.

The hero metric on mobile: Plan tab, top of screen, large text:
"Debt-free by March 2028" with a secondary line "Save £4,200 in interest with Avalanche strategy." That's the motivating hook. Everything else is detail.
